## Evidence and implications

1. **GPU-class PCI devices are represented.** Kerf `src/kerf/init/main.py` maps PCI display class to `pci-display`. Creation accepts PCI addresses or pool node names (`src/kerf/create/main.py`). There is no GPU-specific compatibility validation in that classification. [Pinned Kerf source](https://github.com/multikernel/kerf/blob/49fd9444c2571805dd23160673c3ca4a2a3e3229/src/kerf/init/main.py)

2. **PCI driver handoff exists.** `mk_do_device_remove()` releases the device driver. `mk_do_device_add()` looks up an existing PCI bus and slot, then attaches a driver. It does not itself discover an absent PCI device; missing bus/slot returns `ENODEV`. An explicit override expects the named driver to be registered already. Device add/remove requests can be sent to another kernel. Implication: allocate the P40 before secondary boot for the first experiment, verify enumeration, then load its driver. Dynamic reassignment is a later test. [Pinned hotplug source](https://github.com/multikernel/linux/blob/v7.0-mk2/kernel/multikernel/hotplug.c)

3. **DMA isolation is unfinished.** Upstream issue 18 is an ARM work item, but explicitly states that x86 assigned devices run without an IOMMU inside spawns. This is a concrete GPU-DMA concern, not a reason to assume GPUs cannot work. Inspect the physical host's IOMMU ownership and interrupt-remapping behavior before a GPU trial; do not infer that a global `iommu=off` is required. [Upstream issue](https://github.com/multikernel/linux/issues/18)

4. **The kernel must support spawning.** `CONFIG_MULTIKERNEL` depends on `ARCH_SUPPORTS_MULTIKERNEL` and `KEXEC_CORE`, selects `LIBFDT`, and hands a resource/message-ring manifest to the secondary. Both kernels need the appropriate Multikernel support; using an unmodified older Ubuntu kernel for the P40 is not established. The proprietary driver's build against the chosen kernel must be validated before installation. [Kconfig](https://github.com/multikernel/linux/blob/v7.0-mk2/kernel/multikernel/Kconfig)

5. **A shared filesystem is not yet an inference transport.** DAXFS advertises shared model storage and DMA-buffer backing. That does not establish CUDA host-memory registration or cross-kernel CUDA IPC on Pascal. No dedicated mknet-named driver was found in the inspected Linux tree names; this limited search does not prove networking is absent. Verify the actual network data path before promising unmodified llama.cpp RPC. [DAXFS](https://github.com/multikernel/daxfs/tree/11ab401585b79b4a7c9164019852e0219e197d13)

## Experiment design

Target arrangement:

```text
Primary experimental Linux: 5070 Ti + NVIDIA open driver + inference coordinator
                          |
             verified inter-kernel transport
                          |
Secondary experimental Linux: P40 + NVIDIA proprietary driver + CUDA worker
```

### Gate A: reproducible GPU-free boot

Use a disposable test VM first. Pin sources and hashes; build an independent initramfs and uniquely named kernel in the workspace. Do not copy the production root-device command line. Boot primary and secondary, collect their kernel/CPU/memory identities, verify console access, and repeat teardown/recreation. Confirm resource return. This proves spawning inside a VM, not bare-metal device behavior.

### Gate B: one GPU, one secondary

On a reviewed test environment, assign the P40 before secondary boot. Keep its driver exclusively in the secondary rootfs. Confirm PCI BARs, driver loading, interrupt activity, and UVM. Run a deterministic CUDA test: known integer inputs, device computation, exact CPU-reference comparison, and repeated host/device copies with byte-for-byte comparison. Repeat with pinned host allocations. Require correct results and no NVIDIA Xid, DMA, or interrupt errors before inference.

### Gate C: both CUDA stacks concurrently

Enable the 5070 Ti in the primary. Repeat the correctness workload on both cards concurrently and check that each kernel owns only its intended GPU. Measure each independently before splitting a model. Keep driver libraries/root filesystems separate.

### Gate D: one model

First prove a working transport and use existing llama.cpp RPC semantics as a correctness baseline. If a network interface between kernels is unavailable, networking or a custom transport becomes implementation work, not a launch flag. Only then prototype shared-memory staging to reduce serialization/copies. Validate payload checksums, ownership, synchronization, lifetimes, and pinned-memory compatibility before CUDA DMA through shared buffers. Standard CUDA IPC handles must not be assumed valid across kernels.

The 512 KiB transfer met the <5 ms stretch target in this isolated test.
- Source-backed ring model, checked with `ctypes` structure sizes: 64 slots of 4,120 bytes each; one slot is reserved to distinguish full from empty, leaving 63 usable slots. `mk_message` is 24 bytes and the packed virtio-vsock header is 44 bytes, so each 4,096-byte ring slot carries at most 4,028 VSOCK payload bytes. A 512 KiB payload needs at least 131 data packets/IPIs. The stream credit window is 64 KiB, below the ring's 258,048-byte raw usable capacity. Every packet copies from userspace to an skb, into a temporary `mk_message`, then into the shared ring; receive copies from ring to skb and then userspace. `multikernel_send_ipi_data()` sends an IPI for every packet; it has no coalescing and returns `-ENOSPC` immediately on full. Flow control and userspace retries handle backpressure. There is no descriptor-based bulk buffer today. The matched test shows this kernel path is capable of >200 MiB/s without a ring resize, so a new shared-memory bulk path is not the first optimization.

### Isolated llama.cpp Qwen4exp native-MTP implementation (2026-09-27)

The work is in `/home/shiba/llama.cpp-qwen4exp-mtp`, branch `experiment/qwen4exp-native-mtp` based on `3e88755aa`. The known-good Nemotron/Multikernel llama.cpp branch was not edited, and no P40, Multikernel kernel, NVIDIA driver, RPC pacing or port-5000 change was made. The patch is still experimental and uncommitted. CUDA build `build-mtp-cuda/bin/llama-cli` succeeds with the existing CUDA 12.8 toolchain and RTX SM120 target; the CPU build also succeeds.

The target IQ2_XS GGUF has no MTP tensors. `tools/convert_qwen4exp_mtp_sidecar.py` verifies source-file sizes and SHA-256 against the 31-tensor BF16 MTP manifest, maps 28 draft tensors into a 4.9 GB GGUF sidecar, and intentionally omits the three indexer tensors because the published draft's attention path is dense. It folds zero-centred norm gamma to the GGUF `1+gamma` convention. The target retains ownership of token embedding and output projection. `LLAMA_QWEN4EXP_MTP_GGUF` overlays the sidecar as an extra weight file; the loader rejects duplicate/unexpected names, requires the draft embedding, checks required tensor shapes, and logs every loaded draft tensor with dimensions. The target remains 48 layers; the sidecar adds one draft layer with its own dense attention KV cache. Its graph projects the candidate token embedding and preceding 10,240-wide hyperconnection residual, runs the draft attention and expert FFN, then uses the target output head. The generic `draft-mtp` driver handles proposal, target verification, accept/reject and rollback; no new speculative engine was written.

The draft checkpoint uses hidden width **2,560**, four hyperconnection streams (**10,240** flattened elements), and a **320**-wide HC mixer bottleneck. Both token and hidden projections are 2,560×2,560; the draft attention has Q/K/V projection source shapes 12,288×2,560 / 512×2,560 / 512×2,560, and 2,560×6,144 output projection. Its 512 expert matrices are [512,1,280,2,560] gate/up and [512,2,560,640] down in source storage order. The source manifest lists all 31 shapes; the runtime loader prints the 28 mapped GGUF shapes. The target's final HC residual supplies the draft hidden input, and the draft's own HC residual feeds the next draft step. The draft uses its own positional input and dense KV cache; the target retains its hybrid QSA/recurrent state, with the generic driver's checkpoint restore handling partially accepted verification windows.

An opt-in `LLAMA_MTP_TRACE` trace records committed token IDs and every round's proposals, target-verified IDs/logits, accepted count, rejection position, draft time and target-decode time. `tools/qwen4exp_mtp_correctness.py` asserts the round accounting and compares the full committed-token sequence against a deterministic greedy target-only run.
